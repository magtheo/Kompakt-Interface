## Decision D028 — notes are coordinator-owned objects; scratchpad becomes a mirror

New `notes` table in `coordinator.db`, same pattern as `chat_threads` (D003 precedent). Read model = DB. On create, the existing scratchpad append stays as a **write-through mirror** for Obsidian visibility (two-writer discipline unchanged).

**Rejected:** parsing scratchpad sections at request time — unstable ids (prepending sections shift ordinals; content-hash ids break on user edits), no source links, no filtering, full-file parse per request, and "wire is resource-shaped, never vault-shaped" (D023) forces an abstraction layer anyway.

**Accepted drift:** user edits to a scratchpad section do NOT propagate to the note row. The DB is authoritative for app-facing note objects; the scratchpad is a human-facing projection. Documented here; revisit only if it bites.

**Non-goals (dev plan §Phase5 + §16):** note edit/delete ("do not implement unrestricted vault editing"), vault notes-folder browsing, note→task transitions beyond existing capture interpret.

### Task 1 — schema: `notes` table (src/schema.sql)

```sql
-- Notes (Kompakt Phase 12 / D028). Coordinator-owned object type
-- (D003: chat ≠ agent ≠ task ≠ note). Scratchpad remains a write-through
-- mirror; this table is the app-facing read model.
CREATE TABLE IF NOT EXISTS notes (
    id TEXT PRIMARY KEY,              -- note:{token_urlsafe(9)}
    title TEXT NOT NULL,              -- first line, derived at create
    text TEXT NOT NULL,
    project_id TEXT,
    area_id TEXT,
    source_type TEXT,                 -- chat | agent_run | capture | NULL
    source_id TEXT,
    revision INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

- Fresh AND legacy DBs covered by `CREATE TABLE IF NOT EXISTS` (no ALTERs on existing tables → no V-057 migration class). Add a legacy-DB regression leg to the test (mkstemp DB → old schema → init_database → table exists).
- No index needed at this scale; add `idx_notes_updated` only if list query proves slow.

### Task 2 — create core `src/notes.py`

`create_note(db, *, text, project_id=None, area_id=None, source_type=None, source_id=None, request_id, vault_append=None) -> dict`:

- Idempotency: mutations-table ledger exactly like chat send (V-050 pattern) — replay returns stored result; `complete_mutation(db, id, True, result)` (arg order pitfall!).

- Text caps: title 200 chars, body 10 000 chars (same as W-015 scratchpad caps).
